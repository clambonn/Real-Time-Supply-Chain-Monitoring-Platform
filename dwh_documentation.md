# Data Warehouse & Staging Layer Architecture Documentation

## Overview
This document outlines the initial Data Warehouse architecture for the **Real-Time Supply Chain Monitoring Platform**. The target database `SupplyChain_DWH` is designed as a standalone environment, isolated from the transactional source database to support real-time streaming ingestion via Apache Kafka without introducing workload contention.

---

## Database & Schema Structure

The database utilizes two primary schemas to segregate incoming raw data from processed analytical models:
* **`staging`**: Serves as an ingestion buffer for incoming streaming messages.
* **`core`**: Contains the dimensional data models (Dimensions and Fact tables).

---

## Detailed Data Dictionary

### 1. Staging Layer (`staging.stg_orders`)
Stores raw streaming order events sent by the Kafka Consumer. Data types are selected to seamlessly match the JSON payload generated by the Kafka Producer.

| Column Name | Data Type | Nullable | Primary Key / Constraint | Description |
| :--- | :--- | :--- | :--- | :--- |
| `order_id` | `VARCHAR(50)` | No | PK / UNIQUE | Unique identifier for each order |
| `customer_id` | `VARCHAR(50)` | No | None | Customer identifier associated with the order |
| `order_status` | `VARCHAR(20)` | No | None | Current status (e.g., delivered, shipped, canceled) |
| `order_purchase_timestamp` | `DATETIME` | No | None | Timestamp when the purchase was placed |
| `order_approved_at` | `DATETIME` | Yes | None | Timestamp when payment was approved |
| `order_delivered_carrier_date` | `DATETIME` | Yes | None | Handover timestamp to the logistics carrier |
| `order_delivered_customer_date` | `DATETIME` | Yes | None | Final delivery timestamp to the customer |
| `order_estimated_delivery_date` | `DATETIME` | Yes | None | Estimated delivery timestamp promised to customer |
| `ingested_at` | `DATETIME` | No | DEFAULT `GETDATE()` | Internal timestamp of record insertion into Staging |

### 2. Core Layer (`core` Schema)

#### Dimensions Baseline
* **`core.dim_customers`**: Customer master table.
  * `customer_key` (`INT IDENTITY`, Primary Key)
  * `customer_id` (`VARCHAR(50)`, Unique Constraint)
  * Attributes: `customer_unique_id`, `customer_zip_code_prefix`, `customer_city`, `customer_state`.
* **`core.dim_products`**: Product catalog.
  * `product_key` (`INT IDENTITY`, Primary Key)
  * `product_id` (`VARCHAR(50)`, Unique Constraint)
  * Attributes: Category names (Portuguese/English) and physical metrics (`weight_g`, `length_cm`, `height_cm`, `width_cm`).
* **`core.dim_sellers`**: Merchant directory.
  * `seller_key` (`INT IDENTITY`, Primary Key)
  * `seller_id` (`VARCHAR(50)`, Unique Constraint)
  * Attributes: `seller_zip_code_prefix`, `seller_city`, `seller_state`.
* **`core.dim_date`**: Lookup table for date-based analytical dimensions (`year`, `month`, `quarter`, `day_name`, `is_weekend`).

#### Fact Table Baseline (`core.fact_orders`)
Represents the transactional core fact table. **Note:** Structure created without active ETL/data load for the current stage.
* **Primary Key:** `order_sk` (`INT IDENTITY`)
* **Business Key:** `order_id` (`VARCHAR(50)`, Unique)
* **Foreign Keys:**
  * `customer_key` $\rightarrow$ References `core.dim_customers(customer_key)`
  * `purchase_date_key` $\rightarrow$ References `core.dim_date(date_key)`
* **Metrics & Metrics Attributes:** `is_delayed` (`BIT`), `delay_days` (`INT`).

## Ingestion & Duplicate Handling Strategy

1. **Idempotent Ingestion:** The Stored Procedure `staging.sp_insert_stg_order` handles data insertion from the Kafka Consumer client.
2. **Constraint Enforcement:** Prior to executing `INSERT`, the procedure evaluates:
   $$\text{IF NOT EXISTS (SELECT 1 FROM staging.stg\_orders WHERE order\_id = @order\_id)}$$
3. **Behavior:** If a duplicate `order_id` arrives due to network retries or streaming replays, the procedure safely ignores the duplicate entry without throwing runtime exceptions to the streaming pipeline.
